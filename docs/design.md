# Chat harness PoC: design

Status: agreed 2026-11-12 (grilling session). Owner: platform team.
End-to-end blueprint: [architecture.md](architecture.md).

## 1. Problem

The company's internal chat runs a hand-made ReAct agent (Node/TypeScript): API tools only,
skills fetched by id from a database and pasted into the system prompt. Compared with
ChatGPT, claude.ai or Copilot Chat it cannot discover skills, use MCP servers, work with
files, or run code.

Runtime constraints in the company AKS (Prisma Cloud / Defender):

| Rule | Consequence |
|---|---|
| Container filesystem is read-only, except `/tmp` and PVC mounts | Work files live in `/tmp`; durable files go to Blob |
| No binary downloads | No `pip install` / `npm install` at runtime; everything is baked into images |
| No CLI invocation, even CLIs shipped in the image | No subprocesses at all: no `bash`, `python`, `node`, `chromium` children |
| Pods with HIGH/CRITICAL vulnerable dependencies are killed | Small dependency trees, lockfiles, scan in CI |

Not needed: multi-tenancy (one company, many employees) and durable execution (chat is on
demand; a failed turn is retried by the user).

## 2. Goal

Replace the harness with one that natively supports **skills (progressive disclosure),
MCP, tool calling and a code interpreter**, works with large files, and produces PDF/DOCX/XLSX,
without breaking the Prisma rules. Benchmark two remote-sandbox options for the code
interpreter.

## 3. Decisions

| # | Topic | Decision | Why |
|---|---|---|---|
| H1 | Harness | **Pi 1.5 SDK** (`@earendil-works/pi-coding-agent`, MIT) embedded in a Node API; `SessionManager.inMemory()` per request | Native skills, native MCP (stdio/HTTP, OAuth, `deferred` exposure via `tool_search`), codemode in QuickJS-WASM (no subprocess), small dependency tree. One-day spike against deepagents JS (MIT) on the same scenario before committing. |
| H2 | Rejected | Pi Durable (single writer per SQLite file, not needed); Vercel eve (full server framework with durable "worlds", RC); agent substrate (early development, needs GCS) | Durability and multi-tenancy are not requirements. |
| H3 | Skills | `SKILL.md` folders in a Git repo, published by CI to Blob `/skills/` (read-only); loaded with progressive disclosure. The API's `skills: [ids]` becomes pinned skills | Reviewable by PR; no more database lookup. |
| H4 | Initial skills | `pdf`, `xlsx-csv`, `docx`, `research` (written by us) | Anthropic's document skills are not open source. |
| H5 | MCP | Pi MCP extension, `deferred` exposure; per-session `loadConfig` injects the user's token. | H7 | Database (PoC) | **FerretDB** (Apache-2.0) on the existing CloudNativePG; fallback MongoDB Community if it blocks | MongoDB Community is SSPL (forbidden by the PoC license rule). Encryption is client-side, so the server does not matter. |
| H8 | History | Collection `conversations`; session rebuilt from it each request | In the company this becomes a tool or extension over the existing memory service. |
| H9 | Shell | **just-bash** (Apache-2.0) as the `bash` tool over the conversation workspace; Pi's built-in `bash` disabled | Emulated bash, no subprocess. |
| H10 | Files | Blob container `chat-workspaces`, prefix `<user-oid>/<conversation-id>/`, lifecycle 30 days (account-wide rule, owned by agent-platform-poc); `/tmp/chat/ws/<user>/<conversation>` is a cache restored from Blob when a pod lacks it, changed files uploaded after each turn. Company: same choice unless the storage is reachable from user networks. |
| H11 | Uploaded documents | Parser service turns a file into markdown, saved next to the original (`/docs/<file>.md`); the agent reads it in slices (`grep`/`read`), never whole into the prompt. PoC parser: **markitdown** (MIT); company: their parser (markitdown + Cohere + Document Intelligence). Docling is the upgrade path. |
| H12 | Code interpreter | Remote sandbox, one per conversation, created on first use, destroyed after 15 min idle; outputs copied to Blob after each execution; **no internet egress**; image pre-baked with pandas, matplotlib, reportlab, python-docx, openpyxl, pypdf | Same model as ChatGPT/claude.ai (code + skills in a sandbox). |
| H13 | Sandbox options (benchmark) | **A:** Azure Container Apps dynamic sessions (built-in Python code interpreter; custom container only if packages are missing). **B:** agent-sandbox + Kata on AKS (`SandboxWarmPool` + `SandboxClaim`) | A is managed (preview); B is open source and already proven in agent-platform-poc. |
| H14 | PDF/DOCX | Main path: skill + sandbox. Fallback: in-process `generate_pdf` (pdfmake, MIT, markdown → PDF) | Chromium-based HTML→PDF is a subprocess. Fallback works where no sandbox is approved. |
| H15 | LLM | Existing `llm-gateway` (OpenRouter, key injected by Envoy) | Company: their AI gateway; Pi supports Azure OpenAI natively. |
| H16 | Front end | Streaming HTTP API (SSE) like the company chat would call, plus a minimal web page (chat, upload, download), behind Envoy Gateway with Entra OIDC | Company chat is proprietary. |
| H17 | Supply chain | Trivy (Apache-2.0) in CI fails on HIGH/CRITICAL; pinned lockfiles; minimal base images | Company: twistcli with the runtime rules. |
| H18 | Placement | New repo `chat-harness-poc`, same `aks-lab` cluster, Argo CD; existing storage account `stagentpocjt75` | Reuses ingress, Entra, CNPG, Kata pool, llm-gateway. |
| H19 | User identity | Route-level Envoy `SecurityPolicy` on the chat route: OIDC sign-in (same Entra app) with `forwardIDToken` → JWT validation of the Entra ID token (issuer, audience, JWKS) → `oid` claim to header `x-user-oid`. NetworkPolicy: only the public Envoy reaches chat-api | A route-level policy replaces the Gateway one, so it repeats OIDC. chat-api never parses tokens; the header is set by Envoy and cannot be injected from outside. |
| H20 | Base images | chat-api: `distroless/nodejs24-debian13` (debian12 had a CRITICAL + 6 HIGH in libssl3). Parser: Wolfi python 3.13 packages copied into `scratch` (no shell, no apk, no pip) | Debian python3.13/krb5 carry HIGHs without fixes; Chainguard's free python image is 3.15 and onnxruntime (markitdown → magika) has no 3.15 wheel. Both images: 0 HIGH/CRITICAL in Trivy. |
| H21 | History database | FerretDB 2.7 + `postgres-documentdb` in its own StatefulSet (4 GiB disk); password generated in-cluster by an External Secrets `Password` generator | The existing CNPG cluster has no DocumentDB extension. No secret in git or Key Vault. Company: their MongoDB, same driver. |
| H22 | Probes | HTTP/TCP probes only, no `exec` probes | Nothing is executed inside containers (same rule as the agent). |
| H23 | CI | Build → Trivy (pinned by digest, 0.69.3) → push with buildx; push only if the scan is clean | Plain `docker push` tried cross-repo blob mounts that ghcr denied. Trivy 0.69.4–0.69.6 images were compromised in 2026-03. |
| H24 | Office output (pptx/docx/xlsx) | In-process pure-JS writers: `pptxgenjs` 4.0.1, `docx` 9.14.0, `exceljs` 4.4.0 (all MIT) as tools `generate_pptx`/`generate_docx`/`generate_xlsx`. Design quality lives in the renderer (16:9 grid, type scale, 5 themes + brand override, 14 layouts, chart highlight, text fitting) plus lint warnings fed back to the model; skills `pptx` + `design` teach storyline and choices. Overrides `image-size` 2.0.4 and `uuid` 11.1.1 clear 2 HIGH + 2 moderate advisories | OfficeCli (Apache-2.0) is a CLI binary with embedded .NET: needs a binary download and a subprocess, both forbidden. Kept as a candidate for editing existing files inside the phase 3 sandboxes. Anthropic’s pptx skill is not open source, so ours is written from scratch. Editing existing docx/pptx is not covered (xlsx can be re-read with exceljs). |
| H25 | Web research | Brave Search MCP (upstream `@brave/brave-search-mcp-server` 2.1.4, MIT) as its own pod `brave-mcp`: HTTP transport, stateless, only `brave_web_search`, `brave_news_search`, `brave_llm_context` enabled; API key from Key Vault (`brave-search-api-key`) via External Secrets, mounted as a file; only chat-api may call it, it only reaches 443 out. Overrides `@modelcontextprotocol/sdk` 1.32.2 and `zod` 4.6.7 clear 2 HIGH advisories | Key stays out of chat-api; MCP keeps search swappable (company search, Bing) without code changes. The model loads the tools through `tool_search` (deferred). |
| H26 | Deck design upgrades | Lucide icons (ISC, 2,275, vendored as JSON + tags) drawn as native PowerPoint custom geometry (SVG paths, arcs and circles converted to cubics); 8 more palettes adapted from minimax-ai/skills (MIT); layouts `big_number` and `cards`; dark themes keep dark covers; storylines adapted from ui-ux-pro-max-skill (MIT) | pptxgenjs cannot embed SVG from Node (broken PNG fallback) and resvg-wasm is MPL-2.0, so icons are vectors the renderer draws itself: they render in PowerPoint, Keynote, Google Slides and LibreOffice and take theme colors. Model stays `muse-spark-1.3-contributor` (~R$0,10 per deck): quality comes from the harness (renderer, lint, skills, research), not a pricier model. |
| H27 | Deck themes in the skill + visual self-review without a sandbox | Themes are `skills/pptx/themes/*.json` read on every `generate_pptx` call; the spec can also name a workspace theme file or an inline `{extends, ...}` theme. Every pptxgenjs call is recorded and redrawn on a pure-JS canvas (`pureimage` 0.4.20 MIT, `opentype.js` forced to 1.3.4 MIT via overrides; open fonts Carlito + Gelasio, OFL) into one PNG per slide, returned to the model as tool-result images; the same drawing measures real overflow, text collisions and pixel contrast. Model switched to `deepseek/deepseek-v4.1-flash-1017` (vision, US$0.038/M in, 0.50/M out) | The common harness pattern (model writes code, a sandbox renders with LibreOffice, the model looks at images) needs a subprocess, which the company cluster forbids. Rendering our own recorded layout gives the same review loop in process, ~0.1 s per slide. Themes as data let a skill (or the user) add a brand without a code change. Measured checks already caught real defects: low-contrast delta colors in 12 of 13 themes and an unreadable highlighted table row on dark themes. Preview is approximate (charts/tables simplified, open fonts). `muse-spark-1.3-contributor` also accepts images; deepseek was chosen by the user to compare. |
| H28 | `generate_image` for covers and section openers | One HTTP call through the LLM gateway to `google/gemini-3.1-flash-lite-image` (`IMAGE_MODEL`, OpenRouter `modalities: ["image","text"]`, `image_config.aspect_ratio`); the data URL is saved to the workspace and also returned to the model as an image to check. Prompt guardrails appended in code (no text, logos, charts or real people; leave negative space) plus the theme palette. Max 6 images per session; deck lint warns above 3 `background_image`. `background_image` on title/section/statement/closing/big_number: full bleed (`sizing: cover`) under a 70% scrim of the cover color, so text contrast stays measurable and safe | Covers were flat color + rings; a themed illustration makes decks look designed. Kept narrow on purpose: generated images invent numbers and text, so charts stay native and editable. Measured cost ~US$0.034 per image, ~4 s. No subprocess, no binary, same gateway and egress as chat; Gemini returns JPEG (~60-300 KB). Company use needs a brand/rights check before enabling. |
| H29 | Impeccable as ideas, not as an installed skill; one owner per rule | `pbakaus/impeccable` (Apache-2.0, v4.9) is not installed: its setup runs a downloaded Rust binary (subprocess + binary download, both banned by Prisma), its 62 detectors read HTML/DOM, and its flow (init, PRODUCT.md, three comps to approve) does not fit a chat. Its deck-relevant ideas were adapted with credit: squint test, swap test for generic copy, about four items per group, no emoji as icons, generic labels and icon cards as "generated" tells, light/dark chosen by where the deck is seen. Four became deck lint (same layout 4 in a row, bullets over a third of slides, cards/big_number over 2, emoji). Skills rewritten so each rule has one owner: `design` = any designed file, `pptx` = deck workflow and limits, `reference.md` = fields and lint fixes, `storylines.md` = structures; code limits aligned with the text (5 bullets, 6 agenda items, 6 table columns, 5 pie slices; `background_image` only on title/section) | The user asked for a skill without slop, ambiguity or contradictions. The audit found 20+ conflicts, e.g. `design` banned photos while `pptx` asked for generated covers; agenda allowed at >10 slides vs sections at >12; lint thresholds one above the written limit; the sample `image` layout used a chart picture while charts must be native; storylines started without a title slide. ~64k words of impeccable references would also blow the context budget of a sub-US$1 model. |
| H30 | Dashboards and one-pagers from a spec, numbers computed from the files | `generate_dashboard`: JSON spec (kpi, chart, table, text items in a 4-column grid; global filters; `format` dashboard or onepage) + `.xlsx`/`.csv` in the workspace -> one self-contained `.html`: inline CSS, Apache ECharts 6.1.0 (Apache-2.0; zrender BSD-3) and only the columns the page uses. `dashboard-runtime.js` is the single source of the numbers: the server imports it for lint and the "Computed values" summary, the page inlines it and recomputes on every filter change. Data: exceljs reads xlsx in process (header row detected below title rows, dates to ISO, pt-BR/en number strings typed). Periods on date columns (`"2026"`, `"2026-03"`, `"2026-T1"`, ranges). Same engine exposed as `describe_data` (column profile) and `query_data` (filter/group/aggregate, optional CSV) for Excel questions without a sandbox. Page safety: CSP `default-src 'none'` (no network at view time), text via `textContent`, payload JSON with `<` escaped; served as a download (attachment). Print: A4 landscape (dashboard) / A4 portrait at the exact printable width (one-pager), animation off, charts redrawn on print; height estimate lint matched Chromium print-to-PDF | Employees ask for dashboards and one-pagers. Free HTML written by the model would copy numbers by hand, drift into generated-looking layouts and could not be reviewed without a browser (no subprocess). A spec keeps the look consistent, makes wrong titles visible (the summary showed "Parceiros lideram" while Online led) and needs no sandbox. The `xlsx-csv` skill pointed to a `run_code` sandbox that does not exist yet; `describe_data` + `query_data` close that gap. No image preview yet for dashboards: layout is deterministic and the summary carries the numbers; visual check was done with local Chromium during development only. |
| H31 | Deck art direction: styles + a smaller, curated theme catalog + split/numbered layouts | Themes gain `style`: `classic` (boxed cards, rings: the old look), `editorial` (paper background, rules instead of boxes, serif display in regular weight, half-page picture covers, pull-quote callouts, open KPI figures between hairlines) and `modern` (color-block covers with one geometric form, solid icon tiles, filled callouts, picture covers with a color seam). Catalog replaced: 13 color-only themes -> 9 (executive classic; ivory, graphite, forest editorial; aurora, sunset, tech_night, midnight, volt modern), all contrast-checked. A fourth style `outline` (developer-tool look: hairline panels, label-pill kickers, monospace figures via `monoFont`, activity-grid cover motif) with themes `repo_dark`/`repo_light` (generic names, no third-party brand). New layouts `split` (half-page picture beside title and text) and `numbered` (2-4 items led by large numerals). Picture budget lint counts `background_image` + `split` (max 3). | Users found decks generic: fixed layouts are a company requirement (consistency), so variety must come from art direction inside the layouts, not from free composition. Styles change composition, weight and rhythm, which colors alone cannot. Sonnet 5.5 is being tested in parallel (temporary `LLM_MODEL`) to separate model taste from renderer limits. |
| H32 | Image model: MiniMax H3 at 1K by default, Gemini Flash Lite Image as fallback | `generate_image` speaks both OpenRouter APIs: image-only models (`minimax/`, `bytedance-seed/`, `black-forest-labs/`, ...) via `POST /images` (`b64_json`, `resolution: "1K"`), chat models with image output via `/chat/completions`; `IMAGE_API=chat|images` overrides. Prompt guardrails now ask for the subject in the right half and a calm left third. | Side-by-side test through the gateway, same prompts and theme palettes: Gemini US$0.034 / ~3 s / 1376x768; H3 at 1K or 2K US$0.021 / ~10 s (H3 default renders 5472x3072 at US$0.034, so `resolution` is required). H3 followed the theme palette more closely; Gemini left more empty space for titles (now asked for in the prompt). Both respected no text/logos/faces. |
| H33 | Connectors (phase 2, GitHub first) | Panel "Conectores" in the chat; per-user OAuth (authorization code + PKCE S256, state HMAC-signed and bound to the Entra `oid`, 10 min). Token sealed with AES-256-GCM (AAD = `<user>/<connector>`) under `connectors-master-key` from Key Vault, stored in a separate container `chat-credentials/<user>/<connector>.json`; injected only as the `Authorization` header of the remote MCP (`https://api.githubcopilot.com/mcp/`, deferred via `tool_search`). Read-only by default (`X-MCP-Readonly`); disconnect deletes the blob and revokes the grant | The workspace is readable by the agent, so a token there could be exfiltrated by prompt injection; a separate container plus app-level encryption keeps tokens out of the model's reach and useless if the blob leaks. No new pod: GitHub hosts the MCP. |
| H34 | Multi-user file confinement | Pi's built-in `read`/`write`/`edit`/`ls` are replaced by copies built with `create*ToolDefinition(cwd, {operations})` whose every filesystem call resolves the real path (symlinks included) and allows only the turn's workspace (read-write) and the skills folder (read-only); everything else fails with "access denied". The emulated bash was already confined (virtual FS, no symlinks, no `/proc`). Tests: another user's workspace, `../`, symlink, `/proc/self/environ`, `/etc` | The built-ins accepted absolute paths and `../`: in a pod shared by many users a prompt injection could read another user's files or the pod secrets. Logical isolation inside one process; process/VM isolation stays phase 3. |
| H35 | Stateless turns, 2 replicas | Blob is the only source of truth; `/tmp` holds one turn. Per turn: Blob lease on `_locks/<user>/<conv>` (60 s, renewed every 20 s; a second turn gets 409), wipe and download `<user>/<conv>/*`, run, upload new/changed files and delete removed ones, delete the local copy, release. Downloads, uploads and listings read/write Blob directly. History saves are versioned (`version` field, conditional replace; `ConflictError` 409). Secrets are files in a projected volume (`/var/run/secrets/chat`, mode 0440), not env vars. `ObjectStore` interface: `BlobStore` in the cluster, `FolderStore` locally and in tests | Without affinity any replica must serve any request: the old "use the local copy if present" served stale files across pods, never propagated deletes, filled `/tmp` with every user's files and let two tabs overwrite each other. Proven in the cluster: pod B got 409 during pod A's turn, then read A's file from Blob and ran 2 more turns on it; `/tmp` empty after the turn; no secret in `/proc/self/environ`. Not covered yet: a turn survives only as long as its pod (queue + resumable stream later). |
| H36 | Memory (Hermes-style, 4 layers) | [1] core `USER.md`/`MEMORY.md` (≤ 3 KB, in the system prompt every turn, `memory` tool, ETag writes); [2] episodic `session_search` over the FerretDB history; [3] facts graph: append-only sealed events in Blob are the truth, a per-turn in-process graph (Relate WASM spike, FerretDB fallback) is derived from snapshot + events, typed `remember`/`recall` tools (we write the Cypher, never the model), every fact with source and time, `forget` as an event; [4] learned procedures `skill_save`. A curator (cheap model) extracts facts at turn end. Container `chat-memory/<oid>/`, sealed per user. Full diagram in [architecture.md](architecture.md) §6 | Hermes-like recall without breaking statelessness: no embedded store is ever the truth, so replicas cannot diverge and any pod rebuilds the graph. Relate (Apache-2.0, 10 days old) is evaluated only as the query engine of layer 3, so it can be swapped without touching the tools or the data. |
| H37 | Hybrid memory retrieval | Every turn: core memory (≤ 3.5 KB) + the 5 latest conversations with a curator summary + graph facts about entities the message names (whole-word, accent-insensitive match, ≤ 15 facts), capped at ~3 KB and framed as data. Tools (`recall`, `session_search`) stay for deeper lookups; `session_search` also searches summaries and falls back to the latest conversations. The curator writes a 1-2 sentence summary per conversation (assistant reply allowed as source for *what was done*, filtered like memory) | Tool-only retrieval failed in real use: the model did not call `recall`, and keyword search missed "repositório" vs "projeto". Always-on core + relevance-gated retrieval + tools is the common pattern (ChatGPT memory, Letta core memory, mem0/Zep retrieval) and keeps the token cost bounded (~1k tokens/turn). Proven: a new conversation on another pod answered "qual banco você me recomendou antes?" from the summary. |
| H38 | Reply style | "How to reply" block in the agent system prompt: answer first, size follows the question, no next-step menus or recaps, offer a next step only when context calls for it (needed follow-up, blocking decision, risk), unclear intent → 2-3 lines + one question, no humanizer tells (not-X-but-Y, one-line closers, forced triads, inflated words, emoji). Memory is used silently; procedure saving is offered only when the user signals repetition. Rules adapted from `blader/humanizer` and `i-have-adhd` (both MIT) instead of installing them as skills | Users found the agent too proactive and wordy after every action. Skills load only when the model picks them; tone must apply to every reply, so it lives in the system prompt. Check after deploy: an upload with no request got 2 lines + 1 question; "qual região cresceu?" got one sentence with the numbers. |
| H39 | Files across conversations ("Meus arquivos") and retention | A user's uploads and outputs from other conversations are never mounted automatically. They are listed (panel "Meus arquivos", tool `my_files`) and copied into the current conversation on request (button "Usar", tool `attach_file`) and removed by the user (button ×), always inside the user's prefix, never overwriting (`x (2).xlsx`). Retention: workspace files are deleted 30 days after the **last access** (account `last_access_time_enabled`, rule `chat-workspaces-30d`); the panel shows "expira em N d"; a download of an expired file says so. Old versions under `chat-credentials/` and `chat-memory/` are purged after 7 days (versioning is on), so disconnected tokens and forgotten memory do not survive in versions | Auto-mounting every past upload would spread a prompt-injected document to all future conversations, confuse the context and slow each turn; explicit reuse matches ChatGPT's file library and Claude Projects. Counting from last access keeps files in active use; 30 days is data minimization (LGPD). Proven: a new conversation answered "total daquela planilha que mandei em outra conversa" with `my_files` → `attach_file` → R$ 4,3 mi. |
| H40 | Workspace folders | `uploads/` = user files; `outputs/` = only deliverables the user asked for; `work/` = agent support files (notes, JSON specs, markdown sources, generated images, intermediate CSV). `work/` is persisted in Blob (needed to re-render a deck in a later turn) but hidden from the conversation file panel and "Meus arquivos". Rule in the system prompt and in every skill path; listing filter `userVisible()` in the server | Users saw specs, notes and images mixed with their files. Proven: a docx request wrote `work/ferretdb.md` and the panel showed only `outputs/ferretdb-time-de-dados.docx`. Files from before this change may still show support files in `outputs/` until the 30-day retention removes them. |
| H41 | Portal (React + Vite, ChatGPT-like) | `apps/chat-web` (React 19, Vite 8, react-markdown + remark-gfm + rehype-highlight, mermaid lazy-loaded, lucide-react; all MIT/ISC) built in the chat-api image (`web` stage) and served by chat-api; no CDN.
